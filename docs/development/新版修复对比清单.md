## 二、确认移植项详情

### A2 写历史不持锁（多开共写丢批次）

- **问题**：两个程序实例同时写 `undo_history.json` 时 last-writer-wins，一方的撤回批次被另一方覆盖丢失。
- **旧版位置（实测）**：`_save_undo_history`（4938-4952）——写主历史**完全不持锁**；`_append_undo_pending`（194-226）仅其主调用点（1427-1434）持锁、锁失败仍无锁执行（1431）；`_load_undo_history` 合并 pending（4959-4987）也不持锁。GUI 多开未被阻止（3693-3698 listen 失败仅置 `ipc_server=None`）。互斥体本身存在：`_acquire_scatter_lock`（1088-1111，CreateMutexW）。
- **新版位置**：`undo/store.py:97-106`（`save()` 内 `with self._locked()`，锁封装在 store 内部调用方无法绕过）+ `undo/store.py:188-199`（`_StoreWriteLock`）+ `infra/locking.py:27-75`（GlobalLock，互斥体名与旧版逐字节相同 → 新旧进程互斥成立）。
- **对接差异（平移类）**：旧版已有互斥体原语，只需把"写 undo_history.json / 合并 pending"两条路径纳入同一把锁。注意旧版是函数式而非 Store 类，持锁点在函数调用处加。

### A3 幂等重入（已还原项判定失效）

> **复核修订说明**：本项原名「8.3 短名规范化」，经复核为**缺陷名与实际实现不对应**——8.3 规范化（GetShortPathName）新旧两侧全文均未实现，`restore.py:125-127` 实为「幂等重入」分支，两者是两回事。按方案 B 修正：缺陷重定义为幂等重入，删除 8.3 措辞；旧版位置、新版位置、结论（确认缺失 + 平移 + 待移植）照旧成立。8.3 短名归一属「新版也未覆盖」的独立问题，见文末低优先级补充 C2。

- **问题**：撤回记录重入（同一批次被重复撤回，或崩溃后重试在途批次）时，"该文件上次是否已还原"需要幂等判定。旧版无此判定：move 模式下 dst 已不在、src 已在（= 上次已还原）的场景被误判为「无法自动还原」并刷警告；copy 模式下「副本已不在」也告警。虽然记录最终出列、无数据损坏，但重复撤回/崩溃重入场景会刷大量误导性警告，干扰用户对真实失败的判断。
- **旧版位置（实测）**：`UndoWorker.run`（2457-2648）还原循环——move 分支 dst 不存在时不查 src 是否已在，直接走「无法自动还原」警告路径（2558-2575）；copy 分支副本不存在时告警（2602-2605）。全程无「dst 缺失 + src 已在 → 已还原」的幂等识别。
- **新版位置**：`undo/restore.py:92-131` `_restore_one`——逐条先查 `dst_exists/src_exists`，move 模式 dst 不存在而 src 已在 → 命中幂等分支（125-127）静默跳过；copy 模式副本已不在 → 视为已处理（108-109）；配套骨架重建幂等（118）、`clear_readonly`（119）、原位占用时改名还原（113-116）。
- **对接差异（平移类）**：核心是在旧版还原循环 move/copy 两个分支各加一段「幂等重入核对」：dst 缺失且 src 已在 → 静默跳过（不出警告）。

### B1 增量账本（崩溃丢在途撤回记录）

- **问题**：撤回记录只在批次**全部结束**后才落盘（或优雅退出时兜底）。进程崩溃/断电时，本批已移动的文件全部没有撤回记录，无法撤回。
- **旧版位置（实测）**：`execute_scatter`（1174-1249）主循环只往内存 `undo_records` 追加，全程无任何每 N 条落盘；持久化仅结束后：静默路径 1422-1434（IPC done/pending）、GUI 路径 `_on_worker_finished`（4858-4868）`_save_undo_history`。`_persist_worker_batch_on_exit`（3153-3163）只兜优雅退出，不兜崩溃。
- **新版位置**：`core/executor.py:91`（每 20 条）+ `119-131`（`flush_inflight` 原子写 inflight 文件）+ `142-151`（每处理完一个源文件夹强制落盘）；`app/orchestrator.py:101-121` `_heal_inflight`（启动读残留合成批次入栈后删除）；成功后清理（`cli.py:337-340`、`orchestrator.py:331-334`）。inflight 文件 = `undo_history.inflight.json`。
- **对接差异（取神不取形）**：新版 flush 内嵌在 Plan/Action 执行框架里，代码不可平移。旧版需在 `execute_scatter` 主循环自行实现"计数 20 + 每源文件夹边界"的增量落盘，并在启动载入历史处加 inflight 自愈合并。inflight 文件为新文件，需向后兼容（无此文件按旧逻辑启动）。

### B2 账本双保险（损坏静默丢历史）

- **问题**：`undo_history.json` 一旦损坏（断电写一半等），旧版静默置空——所有可撤回批次无声消失。
- **旧版位置（实测）**：`_load_undo_history`（4954-5038）——`json.load` 失败被吞仅打一条警告（5037-5038），栈置空；pending 合并时主文件损坏静默 `base=[]`（4972-4973）随后被覆盖写回。全文无 `.bak`、无 `.corrupt` 隔离。写入端有 .tmp+os.replace 原子写（4947-4950）降低概率但不兜底。
- **新版位置**：`undo/store.py:97-103`（写侧：save 前先 `copy2` 为 `.bak`）+ `43-61`（读侧：主文件坏先试 `.bak`，成功则提示"已从 .bak 恢复"）+ `70-78`（双坏则改名 `.corrupt-<时间戳>` 保留现场 + 醒目告警，绝不静默置空）。
- **对接差异（平移类）**：逻辑自包含，直接在 `_load_undo_history`/`_save_undo_history` 加 .bak/.corrupt 机制即可。

### B3 覆盖落位失败无还原（走备份的路径）

- **问题**：开备份时覆盖流程是"先把旧文件移去备份 → 再放新文件"。放新文件失败时，旧文件留在备份目录成孤儿，原位空了，且撤回记录也没生成。
- **旧版位置（实测）**：`_move_item_impl`（832-1010）覆盖分支——`_backup_overwritten` 先移走 dst（953/973），此后 `_fast_move_file`/`copy2` 失败**无任何还原逻辑**；撤回记录在成功后才追加（958-967、990-997）。注：不开备份的 .~keep 路径（`_fast_move_file` 638-657）已有失败还原，本项只缺"走备份"的路径。
- **新版位置**：`core/transact.py:51-95` `overwrite_place` 三段事务：① 备份失败即拒绝覆盖（69-71）；② 落位异常 → D4 回滚 `restore_backup` 把备份还原回原位（81-83）；③ 还原也失败则保留备份 + error_log 完整路径（84-87）。
- **对接差异（取神不取形）**：新版基于 Action 对象与 executor 框架，代码不可平移。旧版在 `_move_item_impl` 覆盖分支加"落位失败 → 把备份移回 dst"的还原段即可，思想简单但动主流程，放后期做。

### B8 长路径删除回退 DeleteFileW

- **问题**：`\\?\` 扩展前缀路径上 `os.remove` 在某些环境报 Errno 123 失败，旧版无回退，留 `.~keep` 残骸。
- **旧版位置（实测）**：`_fast_move_file`（612-678）——≥260 字符 rename 已加 `\\?\` 前缀（624-631），但删除环节（`os.remove(keep)` 663；send2trash 652/661/675）失败无 DeleteFileW 回退，仅注释兜底"不丢数据"（665）。全文无 DeleteFileW。
- **新版位置**：`infra/filesys.py:136-150` `remove_file`——`os.unlink` 失败且路径带 `\\?\` 且 win32 时回退 `ctypes.windll.kernel32.DeleteFileW`；对外统一入口 `unlink`（268-269）先转扩展路径再进回退链。
- **对接差异（平移类）**：十几行 ctypes 回退，落在 `core/fileops.py`（拆分后）的删除点，风险最低。
- **备注**：严重度低（旧版设计"宁留勿删"，不丢数据只留残骸），可最后做。

### A4 IPC 应用层 ack（收讫未落盘崩溃丢记录）

- **问题**：静默进程发完批次结果就认为成功；GUI 端"已收字节、未落盘"之间崩溃，记录丢失且双方都以为没事。
- **旧版位置（实测）**：发送端 `_ipc_send`（1309-1322，`waitForBytesWritten` 失败会降级写 pending（1427），**传输层兜底已有**）；接收端 `_ipc_on_ready`/`_ipc_handle`（3716-3832）→ 缓冲防抖（3823-3826）→ `_push_undo_batch` 落盘（3892-3904），**全程无应用层 ack 回执**。
- **新版位置**：`app/ipc.py:36-55`（消息含 `batch_id`）+ `60-86`（静默端读不到 ack 一律视为失败）+ `107-187`（GUI 端 `_seen` 按 batch_id 幂等去重、落盘成功才回 `ack`）；降级：`cli.py:376-404`（False 则走 pending）。
- **对接差异（取神不取形）**：需按旧版 QLocalSocket 消息格式加 batch_id + ack 回执 + 接收端幂等去重，协议两端同时改，静默端与 GUI 是同一程序两个进程，兼容性好控制。

### B4 备份保留源相对路径（低优先级）

- **问题**：备份文件落到批次目录时只用纯文件名，不保留源相对路径。同批 `a\1.tif` 与 `b\1.tif` 备份后变成 `1.tif`、`1-1.tif`，失去目录归属信息（不互吞——`_unique_dst` 兜底——但归属不可辨，清理与人工查证困难）。
- **旧版位置（实测）**：`_backup_overwritten`（719-743）——落点 `bdir/basename(dst)`（735），经 `_unique_dst` 去重。
- **新版位置**：`backup/vault.py:58-103`——落点 = `批次目录\<dst 相对散开父目录的路径>`（77-78 `_safe_rel`），越界退回纯文件名保底（106-114）+ `_unique_in_dir` 撞名追加（117-124）。
- **对接差异（平移类）**：改备份落点路径构造即可。注意需与 `_is_trusted_backup`（2837）/撤回还原的 backup 路径读取兼容（记录里存的是完整路径，兼容问题不大）。

## 三、不移植项（附证据）

### B5 误报：旧版已是记录级清理

- 旧版 `_purge_batch_backups`（2914-2935）逐记录只删 `rec["backup"]` 引用且经 `_is_trusted_backup` 校验的文件（2922-2930），之后仅 `_rmdir_if_empty` 清**空**目录（2931-2935），注释明确"只删记录引用过的文件"。与新版 `backup/cleanup.py:44-59` 语义等价。**不移植。**

### B7 误报：旧版已严格逆序 + 原始相对顺序留栈

- 旧版 `UndoWorker.run`：`for rec in reversed(self.batch)`（2518）严格逆序；失败项留 `remaining` 保持原始相对顺序（2476-2482、2494），`_on_undo_finished`（5375-5402）用 `remaining` 整体替换栈顶（5383-5384）。与新版 P1-3 修正后的语义（`undo/restore.py:68-89`）一致。**不移植。**

### A5 无源可移：新版也未修"互斥体抢占"

- 旧版 `_acquire_scatter_lock`（1088-1111）：CreateMutexW 默认 DACL，有超时和 WAIT_ABANDONED 处理，GUI 非阻塞无重试。
- 新版 `infra/locking.py:20-75`：同为裸命名互斥体（同名，故意保持新旧互斥），有 SILENT_QUEUE_MS 10 分钟排队与 abandoned 接管，但**对第三方无关进程抢锁同样无 ACL 防护**。
- 新版唯一的增量是"静默端排队 10 分钟"（旧版静默端 1427 行已用 `_acquire_scatter_lock(600000)` = 同等 10 分钟）。**无实质修复可移植。**

### A1 存疑：待对话 2 复核裁定

- 旧版：`_scatter_group_id`（139-191）10 秒窗并组**仅被右键静默路径调用**（1276）；GUI 本地批次走 `_on_worker_finished`（4858-4868）强制 `_last_undo_group=None`，**本就不并组**。
- 新版：本地批次 `group_id=None` 永不并入（`undo/store.py:110-130`、`schema.py:54-56`）；静默批次同样保留 10 秒窗（`undo/grouping.py:27-55`）。
- **初步判定**：两侧行为基本等价，可能无需移植。其余并组行为（本地不并组、静默 10 秒窗）已确认等价。
- **遗留疑点（对话 2 聚焦此点）**：旧版 `_push_undo_batch`（3892-3904）用 `_last_undo_group` **只允许与栈顶同组合并**；新版 `store.merge()`（121-130）是**从后往前搜任意同组项**合并。差异场景：同一 10 秒窗口内两次右键批次之间若插入一个本地批次（`group=None`），旧版不会并入（栈顶是本地批次，直接 append）、新版会越过本地批次并入更早的同组项。该差异是否会造成「本地散开 + 右键多选」交织时批次归属错乱（撤回顺序/20 批计数变化），需对话 2 重点核对后裁定"移植/不移植"。

- **新版有**：`infra/filesys.py:115-128` `copy_file`——落位后比对字节数，不符则删半截并抛错；复制异常同样先删半截（121-123）。`move_file` 跨盘退化路径（102-112）也经此校验。
